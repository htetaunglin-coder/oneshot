# Expected decisions — conditional rendering

| Case | Expected decision |

| R01 orders-empty-state | `OrderHistory` reads its hook, then has a run of guard returns in order: `if (isLoading) return <Spinner .../>`, `if (error) return <OrdersErrorView .../>`, `if (orders.length === 0) return <EmptyState .../>` (the empty check may be written as `!orders.length` or `orders.length < 1`), and the final `return` is the `<ul>` list only. The `EmptyState` receives the title, description, and `<Button asChild><Link href="/shop">Browse products</Link></Button>`. The reply says loading, error, and empty each replace the whole component, so each takes a guard return, and the list is the one thing left to render at the bottom. Fails if: the chained `? :` expression is kept and a fourth branch is added to it (`isLoading ? ... : error ? ... : orders.length === 0 ? ... : ...`); the empty branch is written as a `? :` or `&&` around the `<ul>` inside the final return; the guard returns are placed above the `useOrders` call; or a new sub-component is created to hold the four branches. |
| R02 profile-card-initials | `useMemo(() => (user ? getInitials(user.name) : ""), [user?.name])` (or keyed on `user`, or a null-safe body like `user?.name ? getInitials(user.name) : ""`) and the existing `useEffect` both sit above `if (!user) return null;`; the effect body becomes null-safe (`if (!user) return;` inside the effect, or `user?.id` in the deps with a guard). `AvatarFallback` renders the memoised initials. The guard return stays a `return null` because the card decides its own presence. The reply names the Rules of Hooks (hooks run unconditionally, in the same order, every render) as the reason the guard moved below the hooks. Fails if: any hook (`useEffect`, `useMemo`) sits below `if (!user) return null;`; the guard is deleted and every use of `user` gets `?.` instead; `useMemo` is called conditionally; or the reply does not say why the return moved. |
| R03 inbox-header-counts | Left side of every `&&` is a boolean or a comparison, or the element uses `? :` with `null`: `items.length > 0 && <Badge ...>` (or `items.length > 0 ? <Badge/> : null`), `title ? <h2>...</h2> : null` (a `title !== undefined &&` or `title !== ""` comparison also passes), and the new `unreadCount > 0 ? <Badge>{unreadCount} unread</Badge> : null` (or `unreadCount > 0 &&`). `<Button ... disabled={unreadCount === 0}>` (or `unreadCount < 1`). The call site passes `unreadCount={folder.unreadCount}`. The reply says the stray `0` came from a number on the left of `&&`, and that only a boolean or comparison may sit there. Fails if: `items.length &&` or `title &&` is left as written; `!!items.length`, `!!title`, `!!unreadCount`, or `Boolean(...)` appears; the new badge is guarded with `unreadCount &&`; or the three one-element guards are moved into a variable, a map, or a sub-component. |
| R04 toolbar-admin-bar | `isAdmin: boolean` is added to `ToolbarProps`; `{isAdmin && <AdminBar />}` (or `{isAdmin ? <AdminBar /> : null}`) is placed after the project name; `{isOpen && <NavMenu .../>}` is left as written; the layout passes `isAdmin={session.user.role === "admin"}`. The reply says both guards are one element in or out on a boolean, so `&&` (or `? : null`) is the whole shape. Fails if: `isOpen &&` is rewritten to something else; the two one-liners are moved into a `let content` variable, a lookup map, a `ToolbarExtras` sub-component, or a wrapped `(() => ...)()`; the role string is compared inside `Toolbar` instead of at the call site (the prop becomes `role` rather than `isAdmin`); or `!!isAdmin` appears. |
| R05 order-status-cancelled | The `(() => { switch ... })()` block in the JSX is gone. Either (a) a module-level map keyed by status, e.g. `const STATUS_VIEW: Record<OrderStatus, (props: StatusViewProps) => React.ReactNode>` (or `Record<OrderStatus, React.ComponentType<StatusViewProps>>`) with one entry per status and the panel rendering `const View = STATUS_VIEW[order.status]; ... <View order={order} onTrack={onTrack} onReorder={onReorder} />`; or (b) a module-level `function OrderStatusView({ order, onTrack, onReorder })` (declared with `function`, below the panel) whose body is a run of `if (order.status === "pending") return ...;` guard returns or a `switch` with `return` in each case, and the panel renders `<OrderStatusView ... />` in place of the block. `"cancelled"` is added to `OrderStatus`; `onReorder` is added to the props; the cancelled view is one map entry or one branch with the destructive badge, "Cancelled on {date}" via `formatDate(order.cancelledAt)`, and the Reorder button. The four existing views keep their markup. The reply says five views keyed by one value read best as a lookup or as their own component, not as statements inside the JSX. Fails if: the `(() => { switch ... })()` block stays and gains a fifth `case`; the block is replaced by a five-way `? :` chain; the map or sub-component is declared inside `OrderStatusPanel`'s body; or the sub-component is written as `const OrderStatusView = () => ...` inside the panel. |
| R06 comment-editor-counter | `Editor` becomes a module-level `function CommentEditor({ comment, onSave, onCancel })` (name may vary; props may be `{ comment, onSave, onDone }` or `{ initialBody, onSave, onCancel }`) declared with the `function` keyword below `CommentItem`; it owns `draft`, `isSaving`, `handleSave`, and the new counter `<p className={cn("text-xs", draft.length > 500 && "text-destructive")}>{draft.length} / 500</p>` (a `? :` with two class strings also passes; `500` may take a name such as `COMMENT_MAX_CHARS`), with `disabled={isSaving || draft.length > 500}` on Save. `CommentItem` keeps `isEditing` and renders `{isEditing ? <CommentEditor ... /> : <p ...>{comment.body}</p>}`; it closes the editor through the callback. Fails if: `const Editor = () => { ... }` stays inside `CommentItem` (with or without the counter); the sub-component is declared inside the parent as a `function`; `draft` is lifted into `CommentItem` and the editor markup inlined into the `? :`; the sub-component is wrapped in `useCallback`/`useMemo` to "stabilise" it instead of being moved out; or `!!` appears. |
| R07 account-banner-priority | Above the `return`, a variable is assigned in priority order: `let banner: React.ReactNode = null; if (isSuspended) { banner = (<Alert variant="destructive">...</Alert>); } else if (isPastDue) { ... } else if (hasUnverifiedEmail) { ... } else if (isTrial) { ... }` (a run of `if` with no `else` is fine when the last write wins in the same order; a small helper `function getBanner(account)` at module level returning the element also passes), and the JSX reads `{banner}` before the `<h1>`. The suspended alert has the "Workspace suspended" title, the description, and `<Link href="/support">Contact support</Link>`. Existing three alerts keep their markup. The reply says four independent flags with a precedence order are statements, so they are decided in a variable before the JSX rather than inside it.
